# 接入现有包材库

当用户要求“在我的原库新增/修订”时，不用 new_project.py 新建或覆盖原库，不复制 starter 的三款样例覆盖现有数据。

1. 找到用户明确的现有仓库，读取 AGENTS.md 和客户界面档案。核对工作树、最新版本、并发修改与当前线上基线；本套件的源提交只是提取依据，不是今天的线上事实。
2. 原工程曾使用 `docs/client-motion-demo/src` 作为前端，`packaging-assets` 存模型，`model-source/collection` 存源文件。以当前工程真实路径为准。
3. 查找当前原图清单、featured、collection-products、packaging-manifest、素材复制器与相关测试。保留稳定 ID；新增模型只注册该款。旧款名称变更不生成新 ID。
4. 原库历史上有三种不同状态：海报在库、模型已存在、首页是否精选。不能用文件夹里存在 GLB 推断已经正式发布，也不能自动恢复以前撤下的产品。
5. 复用现有包材查看器、延迟加载、取消请求、首帧指标和 GPU 清理。加载壳、场景、详情背景要一致；详情不要拖慢首页。
6. 先本地验证再生成候选包；发布时重新核验线上版本未变化。保留最新其他产品、账户权限、收藏、搜索、原海报、下载及业务接口。不得携带数据库和凭据。
7. 有发布授权时，按现有发布工具执行；归档模型/清单摘要、当前版本、备份和线上验证。检测到线上基线变化则重新合并，不用旧包覆盖新发布。
8. 根据所在仓库要求补测试、更新版本/档案、提交 Git；这些要求属于目标仓库，不扩张到其他项目。推送与部署状态分别报告。

历史示例教训：072 曾有模型但未精选；073 的单瓶/无料体由当次用户明确确认；074–078 不能因本地有文件就声称在线或擅自恢复。这些是定位历史状态的例子，不是新项目的固定 ID 或业务规则。
